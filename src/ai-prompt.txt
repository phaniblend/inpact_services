1)build the architecture
We are refactoring an INPACT-style React learning app.


Current state:
- Lessons are hardcoded in lesson-specific files like inpact_p01_engine.jsx
- A shared shell in inpact_engine_shared.jsx renders the lesson using a config object
- Each lesson currently contains:
  - intro
  - objectives
  - question steps
  - hints
  - feedback
  - seed code
  - evaluation logic


Target state:
- Remove dependency on lesson-specific hardcoded files for runtime
- Keep the shared renderer/shell
- Introduce a backend-driven lesson generation pipeline
- The frontend should request structured lesson JSON from an API
- The API may use AI internally, but the frontend only consumes validated JSON
- Evaluation logic must NOT be executable AI-generated JavaScript on the frontend
- Instead, evaluation should be declarative metadata or use a backend evaluation endpoint


Implement this architecture with clean separation of concerns.


Desired architecture:
1. Frontend
   - DynamicLessonPage / DynamicLessonEngine
   - SharedLessonRenderer (existing engine adapted to render API-provided config)
   - Loading state
   - Error state
   - Config validation / fallback handling
2. Backend
   - POST /api/lessons/generate
   - POST /api/lessons/evaluate
   - schema validation for generated lesson config
   - normalization of AI output before returning to frontend
3. Schema
   - lesson metadata
   - intro
   - objectives
   - steps
   - hints
   - examples
   - feedback templates
   - evaluation rules (declarative, not executable JS)
4. Safety
   - never eval AI-generated code
   - reject malformed lesson JSON
   - provide typed interfaces


Please do the following:
- create a production-oriented folder structure
- define TypeScript interfaces for the lesson schema
- create a sample backend route contract
- refactor the existing shared engine so it can render lesson config fetched from API
- preserve the current UX as much as possible
- include a mock lesson service first, so the app works before wiring a real AI provider
- keep implementation incremental and easy to test


Return:
1. file tree
2. schema/types
3. frontend components
4. backend API shapes
5. migration notes from old local lesson files to new API-driven lessons

14) Strong recommendation on architecture
For quality, use this flow:
lesson request
  → generate lesson blueprint
  → generate intro
  → generate objectives
  → generate each step one by one
  → validate schema
  → store lesson JSON
  → frontend renders shell from stored JSON


Not:
frontend asks LLM for raw lesson on every click


Better:
* cheaper
* versionable
* debuggable
* editable
* stable
